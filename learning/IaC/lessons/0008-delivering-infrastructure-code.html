Delivering infrastructure code

In lesson 0002 every app change took one checked road. Infrastructure code is code, so it can take a road too - but its "artifact" is different, and so are its risks. This lesson builds that road, and sorts out three pairs of words that people mix up all the time.

Warm-up

Where you are

The big idea

Infrastructure pipeline - the one thing
Every infrastructure change gets a reviewed plan, per environment, before apply - instead of applies from laptops.
In a paragraph
The road looks like the app road: pull request, checks, merge, staging, production. Two things differ. First, an infrastructure change has no artifact that works everywhere: its plan depends on the environment's state and reality. So each environment gets its own fresh plan, from the same code version. Second, a plan can destroy data. So the review step reads the plan, not only the code - and rules written as code (policy) check every plan automatically.
Picture
A building permit. You submit the drawing (the pull request). The office checks it against the rules (policy) and a person signs (review). Then the builder checks the actual site again before digging (a fresh plan), because the ground may have changed since the drawing was made.
Where the picture stops working
A permit takes weeks. A good infrastructure pipeline takes minutes, and runs for every small change - small changes are what make it safe (Fowler: small changes rather than batches).

Words you need

pull request (PR)
A proposed change to the repo that others review before it is merged.
speculative plan
A plan made from the PR's code, only to review. It is never applied.
policy as code
Rules written as code that check every plan automatically, for example "no public buckets" (in Spacelift: OPA/Rego).
provisioning
Creating and changing the floor's parts: networks, servers, databases, buckets.
configuration management
Setting up what is inside a server: packages, files, users, services. Ansible is the usual example.
mutable infrastructure
Servers are changed in place while they run.
immutable infrastructure
Servers are never changed. A change means a new image and a new server, and the old one is removed.
configuration as code
Keeping the settings of apps and tools in Git as files: pipeline definitions, Argo CD Applications, feature switches.
GitOps
A way of working where an agent in the target system keeps it equal to a Git repo (Argo CD is one such agent).

Word flag: "configuration as code" is used loosely in the field. In this course it means app and tool settings kept in Git - not infrastructure definitions, and not configuration management.

The road for infrastructure

Follow one change: "turn on versioning for the attachments bucket"

Moment 1 - the pull request

Ana opens a PR that turns on versioning for the S3 bucket of attachments, so that a deleted or overwritten file can be brought back. The pipeline runs a speculative plan and posts it on the PR.

Reveal

Both - and the plan matters more. The code says what Ana meant. The plan says what the tool will actually do in this environment: update in place, or replace the bucket with all its files.

Why: HashiCorp's team workflow does exactly this: review the speculative plan next to the code, to check that the intent is achieved. A one-line code change can produce a -/+ (lesson 0006). Only the plan shows it.

Moment 2 - the policy says no

Ben's PR, in the same week, makes a bucket public so that a partner can download a report. The plan is fine. The policy check fails: "no public buckets".

Reveal

People miss things, rules do not get tired. The policy checks every plan, every time, for the few things that must never happen - public data, missing encryption, a deleted database - and leaves judgement to the people.

Why: policy as code is the infrastructure version of an automatic test. It turns "we agreed never to..." into a check that runs before apply. Ben can still get his report out, but by a safer road the policy allows - for example a link that expires.

Moment 3 - merge, then plan again

Ana's PR is approved and merged. The pipeline plans again against main, for staging.

Reveal

Because the world moved. Other PRs may have merged first, and reality may have drifted since the PR's plan was made. The final plan, made from main and the newest state, is the one that gets applied.

Why: HashiCorp's docs warn that the final plan can differ from the one reviewed on the PR, because of merge order or recent infrastructure changes. A plan is a snapshot. Apply only the plan you just made - and read it if it differs.

Moment 4 - promotion, the infra way

Staging applied fine. Now production.

Reveal

The same code version (the same commit), with production's inputs. Not the same plan: production has its own state and its own reality, so it gets its own fresh plan, which a person approves.

Why: this is the big difference from app delivery. An app artifact behaves the same everywhere. An infrastructure plan is only true for the one environment it was made for. What you promote is the code version and the proof that it worked in staging.

Moment 5 - inside the server

Notekeeper also has one old reporting server (a VM). It needs a security patch. Option A: run Ansible to patch the running server. Option B: build a new server image with the patch and replace the server.

Reveal

Option A, the in-place change. Each run changes a live server. Anything not covered by the Ansible tasks - a hand fix, a package someone added - stays and grows. Option B starts each server from a known image, so drift has nowhere to live.

Why: Fowler: configuration synchronization tries to keep long-lived servers in line, but it can only fix drift in the areas the tool controls. Immutable servers start from scratch every time. Containers (lesson 0003) are the immutable way by default - one reason teams moved to them.

Claim to test

"Run helm list to see what Argo CD deployed."

Reveal

Nothing from Argo CD. Argo CD renders the chart with helm template and applies the YAML itself. No Helm release exists.

Why: one tool owns an app's life cycle. With Argo CD, Argo CD does - look there (argocd app list). With Flux, Helm's own install is used, so helm list does show them.

Say the difference - the same words in every lesson

helm install vs helm template

helm install puts a chart into the cluster and Helm owns its life cycle. helm template only prints the YAML; another tool applies it.

Argo CD uses helm template. So helm list shows nothing.

App repo vs config repo

The app repo holds the code and the Dockerfile. The config repo holds what runs where: charts, values, Argo CD Applications.

Common practice: a code change and a deploy decision get separate commits.

Provisioning vs configuration management

Provisioning creates the floor's parts: networks, servers, databases. Configuration management sets up what is inside a server: packages, files, services.

OpenTofu/Terraform provision. Ansible configures. They often work together.

Mutable vs immutable infrastructure

Mutable: change the live server in place. Immutable: never change it - build a new one and remove the old.

Immutable leaves no room for drift. Mutable is sometimes the only choice for old systems.

IaC vs configuration as code

IaC describes the infrastructure itself. Configuration as code keeps app and tool settings in Git.

Both live in Git and both are reviewed. An Argo CD Application file is configuration as code - and so is a pipeline definition.

App pipeline vs infrastructure pipeline

An app pipeline promotes one artifact. An infrastructure pipeline promotes one code version and makes a fresh plan per environment.

Because a plan is only true for one environment's state and reality.

Cards for your deck

A reviewer approves an infrastructure PR after reading only the code. What did they skip?

The plan - the only place that shows a replace or a destroy for this environment.

The PR plan showed 1 change. The plan after merge shows 3. What do you do?

Stop and read the 2 extra changes: another merge or drift caused them. Apply only a plan you understand.

Why can't you promote the staging plan to production?

A plan is true only for one environment's state and reality. Production gets its own fresh plan from the same commit.

Ben wants a public bucket. The policy blocks it. What is the policy for?

To guard the few things that must never happen, on every plan, even when a reviewer is tired.

Ansible or a new image to patch 50 servers - which avoids drift?

A new image and replacement (immutable). In-place runs only fix what the tasks cover.

Is an Argo CD Application file IaC or configuration as code?

Configuration as code: settings of a tool, in Git. It deploys apps; it does not describe the floor.
