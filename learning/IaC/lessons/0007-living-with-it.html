Warm-up

Where you are

The big idea

Drift - the one thing
Reality changed outside the code - so code, state and reality no longer agree.
Remote state with a lock - the one thing
One shared state, one apply at a time - instead of two people changing the same floor at once.
Module - the one thing
Write a group of resources once and use it with different inputs - instead of copying folders.
Stack - the one thing
A piece of infrastructure you apply as one unit, with its own state - so one mistake cannot reach everything.
Picture
A shared building plan for a chain of shops. One master plan (module), one site book per shop (state per stack), one key to the site office (lock), and a weekly walk around each shop to spot changes nobody wrote down (drift checks).
Where the picture stops working
A shop changes slowly and you can see it. Cloud infrastructure can change in seconds, by a script, a colleague or the provider itself, and you only see it when the tool reads it through the API.

Words you need

drift
Reality changed, but the configuration and the state did not. From 0003 and 0005.
refresh-only plan
plan -refresh-only: shows what changed outside the tool, without proposing changes to the infrastructure.
remote state (backend)
The state file kept in a shared, safe place (for example an S3 bucket) instead of on one laptop.
state lock
While one apply runs, the state is locked. A second apply on the same state must wait or stop.
module
A container for several resources that are used together. You call it with inputs, and you can call it many times.
input variable
A value the caller gives to a module or a stack, for example size_gb or the environment name.
stack
A set of resources applied together, with one state (Kief Morris's word). Terragrunt calls this a unit.
blast radius
How much can break if one apply goes wrong. A smaller stack has a smaller blast radius.
import
Telling the tool that an existing, hand-made object belongs to one of its addresses, so it can manage it from now on.
Terragrunt
A wrapper around OpenTofu/Terraform for many stacks: it keeps shared settings in one place and runs stacks in dependency order.

Three things that must agree

Five team problems

Moment 1 - the Friday fix

On Friday, during an incident, Ben makes the production disk 200 GB in the console. The code still says 100 GB. On Tuesday, Ana applies an unrelated change in the same stack.

Reveal

To set the disk back to 100 GB (or to fail, if the cloud cannot make disks smaller). The tool sees reality (200) differ from the desired state (100) and closes the gap - towards the code, not towards Ben's fix.

Why: the tool trusts the configuration, not the cloud. A hand-made fix that nobody puts into the code will be undone the next time anyone applies. Fowler names it: drift is the street that leads to snowflake servers. The fix is a habit: after an emergency change in the console, change the code the same day.

Moment 2 - spot drift before it bites

The team wants to know about Friday fixes before Tuesday's apply, without changing anything.

Reveal

A refresh-only plan: tofu plan -refresh-only. It reads reality and shows how the state would change. It proposes no changes to the infrastructure.

Why: HashiCorp's drift tutorial uses this exact command to find changes made outside the workflow. Many teams run it on a schedule in a pipeline and alert when it finds drift. Then a person decides: put the change into the code, or apply to remove it.

Moment 3 - two applies at once

Ana and Ben both run apply on the production stack at 10:00, from their laptops. Each has the state file on their own disk.

Reveal

Each one plans from an old copy of the truth, and the second apply can undo or break the first. The fix: keep one shared state in a remote backend, and use a lock, so the second apply must wait until the first is done.

Why: HashiCorp's docs say remote locking makes sure two people do not run at the same time, so each run starts with the newest state. Also: state can hold secrets in plain text, so the shared place must be private and encrypted - never Git.

Moment 4 - copy the folder for staging

To make staging, Ben copies the production folder and changes 12 values by hand. Six months later, staging and production differ in ways nobody chose.

Reveal

Write the resources once, as a module. Give each environment only its inputs: name, size, number of zones. Staging and production then call the same module version with different inputs.

Why: copies drift apart: a fix goes into one folder and is forgotten in the other. Terragrunt's docs give the rule: anything that should differ between environments should be an input variable. Then the only differences are the ones you wrote on purpose.

Moment 5 - one big stack

All of Notekeeper's floor - network, database, API servers, DNS - is one stack with one state. Ana changes a DNS record. The plan also shows a change to the database, because of an old drift.

Reveal

A DNS change would only plan the DNS stack. The database lives in its own stack with its own state, so a DNS change cannot touch it - and its drift waits for a careful, separate review.

Why: one state = one blast radius. Split along how often things change and how bad a mistake is: the network changes rarely, the database is precious, DNS changes often. The price: stacks depend on each other (the API stack needs the network's IDs), so a tool such as Terragrunt runs them in dependency order.

Say the difference - the same words in every lesson

Drift vs a code change not yet applied

Drift: reality changed, the code did not. Unapplied change: the code changed, reality did not.

Both show up in a plan. Only drift needs "who did this, and do we keep it?"

Module vs stack

A module is reusable code. A stack is one applied piece with its own state.

A stack calls modules. Two stacks can call the same module.

Remote state vs Git

State goes in a private, locked, shared store. Code goes in Git.

State can hold secrets and changes on every apply - never commit it.

Refresh-only plan vs normal plan

Refresh-only shows what changed outside the tool. A normal plan shows what the tool will change.

First see the drift, then decide.

Optional lab - a module, two environments (20 minutes)

In ~/iac-lab, make a module and call it twice. Same honest note as 0006: the outputs are what the docs describe - paste what you really see.

mkdir -p ~/iac-lab/modules/floor ~/iac-lab/envs && cd ~/iac-lab
cat > modules/floor/main.tf <<'EOF'
variable "env"     { type = string }
variable "size_gb" { type = number }

resource "local_file" "database" {
  filename = "${path.root}/floor-${var.env}/database.conf"
  content  = "env = ${var.env}\nsize_gb = ${var.size_gb}\n"
}
EOF
cat > envs/main.tf <<'EOF'
module "staging" {
  source  = "../modules/floor"
  env     = "staging"
  size_gb = 20
}
module "production" {
  source  = "../modules/floor"
  env     = "production"
  size_gb = 100
}
EOF
cd envs && tofu init && tofu plan
Reveal

2 to add: module.staging.local_file.database and module.production.local_file.database. One resource block in the module, two calls, two real files.

Why: the address now includes the module call's name. That is how the state keeps the two apart. Note one shortcut in this lab: both calls share one state here. In real work each environment would be its own stack with its own state, as in the figure.

Cards for your deck

An incident fix was made in the console. What must happen the same day?

Put it into the code (or remove it). Otherwise the next apply undoes it.

A nightly job runs a refresh-only plan. What is it for?

To find drift early and alert, before someone's apply undoes or trips over it.

Why is the state never committed to Git?

It changes every apply, it can hold secrets in plain text, and Git cannot lock it.

Ben copied the prod folder to make staging. What is the long-term risk?

The copies drift apart. Fixes reach one and not the other.

Why split the database into its own stack?

Smaller blast radius: changes to other parts cannot plan anything on the database.

A bucket was made by hand two years ago. How does it come under IaC?

Write its resource block, then import it, so the state binds the address to the real bucket.
