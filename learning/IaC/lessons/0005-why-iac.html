Warm-up

Where you are

The big idea

Infrastructure as Code - the one thing
Keep infrastructure in files a tool makes real - instead of clicks and memory.
In a paragraph
IaC treats the floor the way lesson 0001 treated the app. You describe the infrastructure you want in definition files. They live in Git: every change has an author, a time, a reason and a review. A tool reads the files, compares them with what really exists, and makes the API calls that close the gap. Fowler sums it up: infrastructure defined through source code that can then be treated just like any software.
Picture
Lesson 0001's book. A hand-made change to the floor is like a reader writing in one copy of the book: nobody else knows, and the next print run loses it. IaC is the manuscript of the building itself - edit the manuscript, then rebuild from it.
Where the picture stops working
A book does not change after printing. Real infrastructure does: people click, systems fail, the cloud changes things. So the files and reality can drift apart, and a tool must keep checking them against each other (lessons 0006 and 0007).

Words you need

definition file
A text file that describes infrastructure: which resources exist, with which settings. It lives in Git.
ClickOps
Changing infrastructure by hand in the cloud's web console. Fast once, unknown later.
script
A file of steps in order ("create this, then change that"). Imperative.
declarative
Describing the end state ("the disk is 100 GB"). A tool works out the steps. From 0003.
imperative
Describing the steps ("change the disk to 100 GB"). You must know the start state. From 0003.
desired state / actual state
What the files say should exist / what really exists. From 0003.
idempotent
Running it again gives the same result and changes nothing if it is already right.
reproducible
The same files make the same infrastructure, today or next year, for staging or production.
drift
Reality changed, but the files did not. From 0003. Lesson 0007 goes deep.
intent-based provisioning
Asking for infrastructure in plain language and letting an AI tool make the API calls - with no definition files (Spacelift Intent). The contrast in moment 5.

One disk change, done three ways

Moment 1 - by hand

Ben opens the cloud console on Friday evening and changes the production disk from 20 GB to 100 GB. It works. Staging stays at 20 GB.

Reveal

Any two of: who changed it, why, what the old value was, whether staging matches, how to do it again. The change works but leaves no record the team can trust.

Why: ClickOps is fine for one change, once. It fails at scale: a floor of 20 resources, three environments and five people turns into snowflakes - systems that are each a little different, and nobody knows how. Fowler calls such a system a Snowflake Server.

Moment 2 - a script

Ben writes a script that changes the disk to 100 GB. A month later, someone runs the same script to build staging from zero.

Reveal

It fails: there is no disk to change. The script only works from the start state Ben had in mind. To build from zero you need a different script - and another one for each start state.

Why: a script records steps, and steps only work from one known start. Real infrastructure has many possible starts: new, half-made, changed by hand. That is the main weakness of the imperative approach, and the reason most IaC tools are declarative.

Moment 3 - a definition

The team writes one definition file: the database exists, and its disk is 100 GB. They run an IaC tool on staging (no database yet) and on production (20 GB).

Reveal

Staging: it creates the database with 100 GB. Production: it changes the existing disk from 20 to 100 GB. One file, two different start states, the same end state.

Why: the file says where to end, not how to get there. The tool reads the actual state and works out the steps for each start. This is what makes the files reproducible: staging and production come from the same description.

Moment 4 - run it again

The next morning someone runs the tool again on production, with the same file. Nothing has changed since yesterday.

Reveal

Nothing. Desired (100 GB) equals actual (100 GB), so the plan is empty. The tool is idempotent: you can run it any number of times and it only acts where reality differs.

Why: this makes the tool safe to run often - in a pipeline, on a timer, after an incident. A script that says "add 80 GB" would make the disk 180 GB on the second run. A definition that says "100 GB" cannot.

Moment 5 - just ask the AI?

Ana has heard about Spacelift Intent: you ask an AI in plain language ("give staging a 100 GB database"), and it makes the API calls with no definition files, while policies and an audit trail still apply.

Reveal

A reviewed, repeatable description of the end state. There is a record of what was done, but no file that says "this is what staging must look like", that you can review line by line, change in a pull request and apply to a new environment.

Why: Spacelift itself positions Intent for non-critical work (experiments, proofs of concept), next to IaC for production, and lets you export what Intent built as Terraform or OpenTofu code later. So even its makers treat the definition file as the long-term home of important infrastructure.

Say the difference - the same words in every lesson

Imperative vs declarative

Imperative: you give the steps. Declarative: you give the end result, and a tool works out the steps.

Steps need a known start. An end result works from any start.

Application code vs infrastructure code (settled)

Application code says what the app does. Infrastructure code says what the floor is made of.

Both live in Git, both get reviewed, both go through a pipeline.

IaC vs intent-based provisioning

IaC keeps a reviewed file of the end state. Intent-based provisioning asks an AI to make the calls, with no such file.

Spacelift positions Intent for non-critical work, and lets you export to code.

Idempotent vs repeatable script

Idempotent: running again changes nothing if it is already right. A script repeats its steps every time.

"Disk is 100 GB" is idempotent. "Add 80 GB" is not.

Imperative or declarative?

Steps or end state? The first click counts.

Cards for your deck

Ben fixed production by hand on Friday. What is missing on Monday?

A record: who, why, the old value, and whether staging matches. The change lives only in reality and in Ben's head.

A script that worked in production fails on a new staging. Why?

Its steps assumed production's start state. A definition works from any start.

Why is "the disk is 100 GB" safer to run twice than "add 80 GB"?

It is idempotent: the second run sees 100 = 100 and does nothing.

Staging and production must have the same floor. What gives you that?

One set of definition files applied to both, with per-environment inputs (lesson 0007).

A colleague says: "With AI we do not need IaC files any more." What do you ask?

"Where is the reviewed description of the end state? How do we rebuild staging from it?" Even Spacelift exports Intent to code for important work.

What is a snowflake server?

A system made by hand, a little different from all the others, and nobody knows exactly how.
