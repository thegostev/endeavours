Warm-up

Where you are

The big idea

Plan - the one thing
Know exactly what will change before anything changes - instead of finding out in production.
State - the one thing
A record that binds each resource in your files to one real object - instead of guessing which object is which.
In a paragraph
You write resources in configuration files. init downloads the providers: plugins that know one platform's API. plan reads your files and the state, asks each provider what really exists, and lists the difference as steps. apply makes those steps real, in the right order, and writes the new IDs into the state. Next time, the state tells the tool which real object each resource is.
Picture
A builder with a plan drawing and a site logbook. The drawing is your files. The logbook says "wall W1 is the one we built on 3 March". Before work starts, the builder walks the site, compares it with the drawing and the logbook, and writes a work list for you to sign.
Where the picture stops working
A builder can see a wall and know it is W1. A cloud API cannot always tell which object you mean: names can repeat, and not every resource has tags. The tool cannot see your intent, so the logbook (state) must say which object is which. Lose the state, and the tool no longer knows what it built.

Words you need

resource
One thing the tool manages, written as a block in a file: resource "local_file" "database" { ... }.
address
A resource's name in the code: type plus name, for example local_file.database.
configuration
All the .tf files in one folder. The desired state.
provider
A plugin that turns resources into API calls for one platform. Here: local (files on your disk) and random (random names). In real work: aws.
init
The first command in a folder. It downloads the providers the configuration asks for.
state
A file (terraform.tfstate) that records, for each address, the ID and values of the real object it made.
plan
A preview: what will be created, changed, replaced or destroyed. Nothing changes yet.
apply
Makes the plan real, then updates the state.
dependency
One resource needs another's value first. The tool reads the references and works out the order.
update in place vs replace
In place: the real object is changed and keeps its ID. Replace: the old object is destroyed and a new one is made.

Word flag from the glossary: "provider" here always means the plugin. AWS the company is the "cloud provider".

The engine

How to read a plan: five symbols

SymbolMeaningRisk for a database
+createLow - something new appears
~update in place - same object, new valuesLow to medium - read the values
-destroyHigh - it will be gone
-/+replace: destroy first, then create a new oneHighest - the data goes with the old one
+/-replace: create the new one first, then destroy the oldHigh, but no gap in service

The last line of every plan sums it up, for example Plan: 1 to add, 0 to change, 1 to destroy. A replace counts as one add and one destroy. Train your eye: read that line first, then look for - and -/+.

Set up the lab (5 minutes)

Install OpenTofu with Homebrew, then make a folder. (Install options: OpenTofu docs.)

brew install opentofu
tofu version
mkdir -p ~/iac-lab/floor && cd ~/iac-lab/floor

Make the configuration file. Copy the whole block and paste it in the terminal - it writes main.tf.

cat > main.tf <<'EOF'
terraform {
  required_providers {
    local  = { source = "hashicorp/local", version = "~> 2.5" }
    random = { source = "hashicorp/random", version = "~> 3.6" }
  }
}

# A random two-word name, like a cloud resource ID
resource "random_pet" "db_name" {
  length = 2
}

# A file that stands in for Notekeeper's database
resource "local_file" "database" {
  filename = "${path.module}/floor/database.conf"
  content  = <<-EOT
    name    = notekeeper-${random_pet.db_name.id}
    size_gb = 20
  EOT
}
EOF
Walk me through main.tf
  • terraform { required_providers ... } - which plugins this folder needs, and which versions.
  • random_pet.db_name - asks the random provider for a two-word name. It stands in for an ID that a cloud makes for you.
  • local_file.database - asks the local provider for a file. It stands in for the database: its content holds the name and the size.
  • ${random_pet.db_name.id} - a reference. The file needs the name first. That is a dependency.

Why files and random names? They behave like real resources for the engine - created, read, changed, destroyed through a provider - but cost nothing and break nothing.

The lab

Step 1 - init

tofu init
ls -a
Reveal - what the docs say you will see

The two providers, local and random, into a hidden .terraform folder. It also writes .terraform.lock.hcl, which pins the exact provider versions.

Why: the core knows no cloud at all. Everything platform-specific lives in providers, and each folder says which ones it needs. The lock file makes sure your colleague and the pipeline get the same versions - lesson 0001's "same bytes everywhere", for tools.

Step 2 - the first plan

tofu plan
Reveal - what the docs say you will see

2 to add, 0 to change, 0 to destroy. The name is not known yet: the plan shows (known after apply) for the file content, because the random name does not exist yet.

Why: a plan can only show what it can know before acting. Values made by the platform (IDs, random names, addresses) appear only after apply. When you review a real plan, "known after apply" means: the plan cannot promise this value.

Step 3 - apply

tofu apply
# type yes when asked
cat floor/database.conf
ls
Reveal - what the docs say you will see

terraform.tfstate - the state. Open it: you will see both addresses with their real values, including the random name.

Why: the state is how the tool remembers that local_file.database is this exact file and random_pet.db_name is this exact name. HashiCorp's docs call this mapping to the real world the primary purpose of state.

Step 4 - apply again

tofu apply
Reveal - what the docs say you will see

Nothing. It reports no changes: your infrastructure matches the configuration.

Why: this is idempotency from lesson 0005, now on your screen. Desired equals actual, so the plan is empty. You can run it a hundred times.

Step 5 - make the disk bigger

sed -i '' 's/size_gb = 20/size_gb = 100/' main.tf
tofu plan
Reveal - what the docs say you will see

Replace: -/+, "1 to add, 0 to change, 1 to destroy". The local provider cannot edit a file in place: any change to its content means "delete the file, write a new one". The random name stays, because nothing about it changed.

Why: whether a change is in place or a replace is decided by the provider, setting by setting - not by you, and not by how small the change looks. For a file, replace is harmless. For a database, the same symbol can mean the data is gone. That is why you read the plan before every apply. Run tofu apply now to accept it.

Step 6 - someone deletes it by hand

rm floor/database.conf
tofu plan
Reveal - what the docs say you will see

Create it again: "1 to add". Before planning, the tool reads the real objects. It finds the file missing, notes that objects changed outside the tool, and plans to bring reality back to the desired state.

Why: every plan starts by refreshing: it asks the providers what really exists, and compares three things - configuration, state, reality. A hand-made change shows up as a difference. This is drift, and lesson 0007 is about living with it. Run tofu apply to put the file back.

Step 7 - your experiment, then clean up

# Edit the file by hand instead of deleting it:
echo 'size_gb = 999' >> floor/database.conf
tofu plan

# When done:
tofu destroy
No answer here on purpose. In step 6 you deleted the file. Now you change its content by hand instead. Does the plan notice? What does it propose? Paste the first 10 lines of your plan in chat. Then tofu destroy: count how many resources it says it will destroy before you type yes.

Read a real-looking plan

This is a short example of a plan for Notekeeper's production database on AWS. Someone renamed the database in the code to make the names neater.

  # aws_db_instance.notes must be replaced
-/+ resource "aws_db_instance" "notes" {
      ~ id         = "db-ABCD1234" -> (known after apply)
      ~ identifier = "nk-prod" -> "notekeeper-prod" # forces replacement
        # (40 unchanged attributes hidden)
    }

Plan: 1 to add, 0 to change, 1 to destroy.

Reading - the neat rename

Reveal

The database nk-prod is destroyed and a new, empty notekeeper-prod is made. The comment forces replacement shows which line causes it. Unless a backup is restored, the notes are gone.

Why: a tiny, harmless-looking code change can mean a replace. The plan is the one place where this shows before it happens. That is why teams protect important resources: cloud settings such as deletion protection, and the tool's own prevent_destroy setting, which makes any plan that would destroy the resource fail.

Say the difference - the same words in every lesson

Configuration vs state vs reality

Configuration: what you want. State: what the tool recorded it made. Reality: what really exists now.

A plan compares all three. When they disagree, you have work to read carefully.

Plan vs apply

Plan shows what would change. Apply changes it.

Apply shows the plan again and waits for yes - the last chance to read it.

Update in place vs replace

In place: the same object gets new values. Replace: the old object is destroyed and a new one is made.

The provider decides, per setting. Look for -/+ and forces replacement.

Provider vs cloud provider

A provider is a plugin that calls one API. A cloud provider is a company like AWS.

The aws provider is the plugin that calls AWS.

Cards for your deck

A plan says "0 to add, 3 to change, 0 to destroy". What do you read first?

The three ~ blocks and their old -> new values. No destroy - lower risk, but check what changes.

A plan for the production database shows -/+ and forces replacement. What do you ask?

"Which line forces it, is it needed, and what protects the data?" Replace = the data goes with the old database.

You lose terraform.tfstate. What does the next plan think?

That nothing exists yet: it plans to create everything again, next to the real objects it can no longer recognise.

Why does tofu apply twice in a row do nothing the second time?

Desired equals actual: idempotency.

What does the aws provider do?

It turns resources in your files into AWS API calls, and reads real objects back.

Someone deletes a resource by hand. What does the next plan propose?

To create it again - the plan refreshes, sees it missing, and closes the gap.
