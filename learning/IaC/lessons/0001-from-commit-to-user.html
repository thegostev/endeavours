From a code change to a user

What actually happens between a developer writing code and a user using it? Four things, three steps, and one floor under them. This is the core of the onion. Every later layer adds detail to this picture - it never replaces it.

Where you are

The big idea

Software delivery - the one thing
Get a code change to users safely and repeatably - instead of by hand and hope.
In a paragraph
A developer records a change. A build turns the code into a packed, fixed artifact. A deployment puts that artifact, with its config, into an environment, where it becomes a running app. A release lets users use the new feature. Under all of it is the infrastructure: the servers, network and storage that every environment stands on.
Picture
Publishing a book. The manuscript edit is the change. Printing makes identical copies that nobody can edit (the artifact - a fix needs a new print run with a new edition number). Putting copies on the shelf of one shop is the deployment. Launch day, when buyers may take it, is the release. The shop building and its shelves are the infrastructure.
Where the picture stops working
A running app is not a book on a shelf. It is a live process that uses CPU and memory every second, and it can crash. Copies cost nothing, so teams deploy many times a day and can take a version back in minutes. And in software, the building itself can be written down in files and rebuilt. That last point is the whole reason for Infrastructure as Code (Layer 5).

Words you need

repo
Short for repository. The place where code is kept with its full history (version control, for example Git).
change
One recorded edit to code, with an author, a time and a reason. In Git: a commit.
build
The step that turns code from the repo into an artifact.
artifact
What a build makes: a packed, versioned app that nobody edits after it is made. Example: notekeeper-api:1.4.0.
store
The place where artifacts are kept until they are used (an artifact repository or image registry).
environment
One place where a copy of the app runs for one purpose: dev, staging or production. It is infrastructure plus its own config.
config
Values that change between environments: the database address, keys, switches. Kept outside the artifact.
deployment
Putting one artifact into one environment, so it runs there.
running app
The artifact while it runs as processes in an environment, with that environment's config.
release
Letting users use a change.
switch
A config value that turns a feature on or off inside a running app. The usual name is feature flag or feature toggle - from lesson 0002 on, the course uses "feature flag". Lesson 0002 shows its second job: letting unfinished code sit in production, switched off (Trunk Based Development: Feature Flags).
infrastructure
The computers, networks and storage that environments are built on.

Word flag: Twelve-Factor uses "release" for "build plus config, ready to run". In this course, "release" always means the step to users. When you read Twelve-Factor, read its "release" as "the artifact plus config of one deployment".

The running example: Notekeeper

We use one small system in every lesson, so each new layer changes something you already know. Notekeeper lets people write and keep notes. It has three parts.

Follow one change: "pin a note"

Ana, a developer, adds a "pin note" button to the web app and the API code behind it. Five moments. At each one, type a bet first - a guess of "?" counts - then open the reveal.

Moment 1 - the merge

Ana's change is reviewed and merged into the main branch of the repo. Production still runs version 1.3.9.

Reveal

No. A change is text in the repo. Nothing runs from the repo. Users only touch a running app, and the running app is still 1.3.9.

Why: what runs must be fixed and known. If production ran straight from the repo, every new merge would change production at once, with no check and no way to say "this exact version is live". Twelve-Factor says it directly: you cannot change code at runtime - any change must go through a new build.

Moment 2 - the build

The merge starts a build. It makes notekeeper-api:1.4.0 and notekeeper-web:1.4.0 and puts them in the store. A tester then finds a small bug in the API.

Reveal

No. Nobody edits an artifact after the build. The fix is a new change in the repo, and a new build: 1.4.1.

Why: if an artifact could change, "1.4.0" would mean different bytes on different days. Then nobody could say what was tested, what runs, or which version to go back to. A fixed artifact is what makes "go back to 1.3.9" safe: 1.3.9 is still in the store, exactly as it was.

Moment 3 - two environments, one artifact

1.4.1 is deployed to staging. Testers try it. Then the same 1.4.1 is deployed to production. Staging uses a test database. Production uses the real one.

Reveal

From config. Each environment gives the running app its own values (the database address, keys, switches) at deployment. The artifact does not know where it runs.

Why: the point of staging is to test the thing that will go live. If each environment had its own build, staging would test a different thing from what production runs. So: one artifact for every environment, and the differences live in config.

Moment 4 - deployed, but off

1.4.1 runs in production. The pin button is behind a switch, and the switch is off. Marketing wants the feature on Monday at 09:00.

Reveal

Deployed: yes. Released: no. The code runs in production, but no user can use it. On Monday someone turns the switch on. That is the release - and it needs no new deployment.

Why: deploying and releasing have different risks and different owners. Deploying is a technical step: do it when it is quiet and easy to undo. Releasing is a product decision: do it when users, support and marketing are ready. If the feature goes wrong, turn the switch off - a config change, faster than a new deployment. (Feature Toggles: release toggles separate deployment from release.)

Moment 5 - the floor changes

A month later, the database disk is almost full: 20 GB, and the notes keep coming. The team must give the database 100 GB.

Reveal

None of the four. No code changes, no new artifact, no new deployment. The floor changes: the infrastructure under the production environment.

Why: the four things describe the life of the app. Infrastructure has its own life: it gets bigger, it gets new parts, it breaks. And every environment stands on it, so a mistake here can hurt every version at once.

The open question - no answer here on purpose. For 1.4.1 the team knows who changed what, why, when, and how to go back. Now the disk change: how would a person make it today, if the team had no special tool? Afterwards, what would the team know about that change - and what would it not know? In a Kubernetes shop

The four things and three steps of this lesson, as a Kubernetes company runs them.

Four things, three steps - for real

This lesson's idea in a real Kubernetes company. Common practice, not every company. The whole chain, with figures: The real chain.

Change
A Git commit in the app repo
Build
A CI job (GitHub Actions, GitLab CI): tests on the code, then docker build
Artifact
A container image: notekeeper-api:1.4.2@sha256:9f2c…
Store
An image registry, for example Amazon ECR
Deployment
A commit to the config repo ("prod runs 1.4.2"), then an Argo CD sync
Release
A feature flag turned on, or a canary with Argo Rollouts
Floor
VPC, EKS cluster, RDS database - built with OpenTofu or Terraform, on their own road
Not everyone
Serverless shops ship a zip to Lambda; VM shops ship a machine image (AMI). Same four things, different box.
Sources
Kubernetes: Images, Argo CD: overview

Claim to test

"The container moves from the laptop to CI, to the registry, to Kubernetes."

Reveal

The image moves. A container never moves. The image is copied from CI to the registry and pulled by each node. A container is one running copy of it, on one node.

Why: image vs container is this lesson's pair, artifact vs running app, one level down. The artifact travels; the running app lives in one place.

Say the difference - the same words in every lesson

Image vs container

The image is the fixed package in the store. The container is that image running.

The image moves (CI → registry → node). A container never moves.

Build vs deploy vs release

Build makes the thing. Deploy puts the thing in a place. Release lets users use it.

They can happen at three different times. Moment 4 is the proof.

Artifact vs running app

The artifact is the packed, fixed thing in the store. The running app is that artifact alive in an environment, with that environment's config.

One artifact, many running apps: one per environment.

Infrastructure vs environment

Infrastructure is the floor: servers, network, storage. An environment is one use of it for one purpose: infrastructure plus config.

Several environments can share one infrastructure, or each can have its own. "Platform" is a third word, for Layer 6 - not the same as either.

Application code vs infrastructure code (a first look)

Application code says what the app does. Infrastructure code says what the floor is made of.

Moment 5 had no infrastructure code - that is the open question. Layer 5 is about it.

What breaks where

Cause and effect, the way an engineer thinks about it in an incident.

What failsWhat users noticeWhy
The build (a test fails, the code does not compile)Nothing. Production still runs 1.3.9No new artifact, so there is nothing new to deploy
A deployment to productionIt depends on how you deploy (Layer 2). With a safe method: little or nothingGoing back means deploying the last good artifact. It is still in the store, unchanged
A release (the pin feature has a bug)Users see the bug, until the switch goes offTurning a switch off is a config change - no new build, no new deployment
The infrastructure (the disk is full, a server is gone)Everything on that floor can stop - every versionEvery running app in that environment stands on it

Look at the last row. It is the widest blast radius, and in moment 5 it was the one change with no recorded, repeatable path. Keep that in mind.

Cards for your deck

Ana merges her change. A user asks why the new button is not there. What is the first question you ask?

"Was it built and deployed - and is the switch on?" A merge only changes the repo. Users touch a running app.

A tester finds a bug in 1.4.0, which is in the store. What does the fix look like?

A new change and a new build: 1.4.1. Nobody edits an artifact, so 1.4.0 stays a fixed, known version to go back to.

Staging passed. Someone wants to make a "production build" for go-live. What is wrong with that?

Production would run something staging never tested. One artifact for all environments. Differences go in config.

A new feature causes complaints an hour after release. What is the fastest safe step, if it is behind a switch?

Turn the switch off. That is a config change - no build, no deployment.

Production broke after a deployment. How do you go back?

Deploy the last good artifact. It is still in the store, unchanged. Rollback is a deployment.

Why can one infrastructure problem hurt more than one bad deployment?

A bad deployment hits one version in one environment. The floor holds every running app on it, whatever the version.
