Warm-up

Where you are

The big idea

Container - the one thing
Give the app the same predictable box everywhere - instead of "it works on my machine".
In a paragraph
An app needs more than its own code: libraries, a language runtime, files, settings. A container image packs all of it into one fixed artifact. A container is that image running as an isolated process. A virtual machine is heavier: a whole pretend computer with its own operating system. An orchestrator such as Kubernetes runs many containers on many machines and keeps the right number of them alive.
Picture
A shipping container. The port does not care what is inside: every container has the same shape, so the same crane moves it onto any ship.
Where the picture stops working
A steel container is closed and does nothing. A software container is a live process that shares the machine's operating system kernel with its neighbours, so the walls are thinner than steel. That is why containers are light, and why a VM is the stronger wall.
Desired state - the one thing
You write what should be true; a loop makes it true and keeps it true - instead of you doing each step.

Words you need

process
A running program. The operating system gives it CPU time and memory.
operating system (OS)
The base software of a computer (for example Linux). Its core, the kernel, shares the hardware between processes.
virtual machine (VM)
A pretend computer made by software (a hypervisor) on a real one. It boots its own full OS.
container image
The artifact form for containers: a fixed, layered package of the app and everything it needs. Example: notekeeper-api:1.4.2.
container
A container image while it runs: an isolated process that shares the machine's kernel.
orchestrator
Software that runs containers on many machines and keeps them running. Kubernetes is the best-known one.
desired state
What you say should be true, written down ("3 copies of the API"). In Kubernetes: the object's spec.
actual state
What is really true right now ("2 copies run"). In Kubernetes: the object's status.
controller
A loop that watches the actual state and acts to move it toward the desired state, forever.
imperative / declarative
Imperative: you give the steps ("start one more"). Declarative: you give the end result ("3 should run") and a tool works out the steps.

Kubernetes words you know from work (pod, deployment, service) are not needed for the bets. Where they help, the reveal names them.

Two ways to share one server

Follow Notekeeper's API

Moment 1 - works on my machine

1.4.2 of the API runs fine on Ana's laptop. On the staging server it crashes: the server has an older version of a library the API needs.

Reveal

The image carries its own copy of the library. The API no longer uses what happens to be installed on the server. It runs with exactly what was packed at build time.

Why: this is lesson 0001's artifact idea, taken one step further. The artifact now includes the app's surroundings, not only its code. Docker's guide puts it this way: because everything the app needs is inside, a container does not depend on what is installed on your machine.

Moment 2 - VM or container for the API

The team needs to run 6 copies of the API. Option A: 6 VMs. Option B: 6 containers on 2 servers.

Reveal

Containers. Each container is a process on a shared kernel. There is no OS to boot, so it starts in about a second, and many fit on one machine. Each VM must boot a full OS of its own.

Why: a VM copies a whole computer, a container copies only the app's box. The price is a thinner wall: containers on one machine share one kernel. When a strong wall matters (different customers, strict security), teams use VMs, or containers inside VMs.

Moment 3 - a server dies

Kubernetes runs 3 copies of the API: 2 on server A, 1 on server B. At 03:00, server A loses power. Nobody is awake.

Reveal

A controller sees 1 copy running where 3 are wanted, and starts 2 more on server B. First Kubernetes waits a few minutes to be sure server A is really gone. No person acts. In Kubernetes words: the Deployment's ReplicaSet controller creates new pods.

Why: you wrote the desired state (3 copies), not the steps. The controller compares desired with actual all the time, like a thermostat compares the room with the dial. Kubernetes' own docs use that picture. The fix happens whatever broke it, at 03:00 or at noon.

Moment 4 - a hand-made change

Git says the API runs 3 copies, and Argo CD syncs from Git. During a busy evening, Ben runs kubectl scale --replicas=5 by hand.

Reveal

Argo CD sees that the cluster no longer matches Git. It marks the app OutOfSync. With automatic self-heal on, it sets the count back to 3. Without self-heal, the 5 copies stay until the next sync - and the record in Git is wrong in the meantime.

Why: only one place can say what is true. Here it is Git. A hand-made change makes the actual state drift away from the written desired state. This is drift, and it is one of the main problems IaC must handle (lesson 0007). Kubernetes' docs warn against mixing ways of managing one object for the same reason.

Moment 5 - where does the database run?

Ana asks: should Notekeeper's database also be a container in the cluster, next to the API?

Reveal

Its data must survive. The API can be thrown away and started again from the image any time. A database holds the notes: it needs backups, safe disks and careful upgrades. Many teams therefore rent a managed database from the cloud instead of running it in a container.

Why: stateless parts (the API) are easy to replace, so containers and controllers handle them well. Stateful parts (the database) are hard to replace. That is why lesson 0004 puts the database on the floor as a managed service - and why HwtP for Infra releases databases and buckets differently from apps.

What actually runs - for real

This lesson's idea in a real Kubernetes company. Common practice, not every company. The whole chain, with figures: The real chain.

Container
Runs inside a Pod: one or more containers that share an address. Kubernetes schedules Pods.
Desired state
The Deployment's spec (replicas: 3, the image), stored by the API server
Controller chain
Deployment → ReplicaSet → Pods. The scheduler picks a node; the kubelet on it starts the containers.
Container runtime
containerd (the box in the figure above). Docker builds images, but nodes do not run Docker any more.
Server dies (moment 3)
The ReplicaSet makes new Pods; the scheduler puts them on healthy nodes
Process crashes
The kubelet restarts that container on the same node
Sources
Kubernetes: Pods, Kubernetes: Controllers, Dockershim removal FAQ, AWS: containerd on EKS

Claim to test

"When a node dies, Kubernetes restarts the container on another node."

Reveal

Nothing moves or restarts - a new Pod is made. The ReplicaSet makes it, the scheduler places it, the new node's kubelet starts fresh containers from the image.

Why: restart is the same-node fix for a crashed process. A lost node means replace. Containers are throw-away, so replacing is safe.

Claim to test

"Kubernetes nodes run containers with Docker."

Reveal

False. Kubernetes removed the dockershim in 1.24. EKS node images from 1.24 on use containerd only.

Why: build and run are separate jobs that share one image format (OCI). An image built with Docker runs fine under containerd.

Claim to test

"A Pod can be running and still get no traffic."

Reveal

True. The Service sends traffic only to ready Pods. Until the Pod's readiness probe passes, it runs but gets no requests.

Why: running and ready are two different checks. Readiness is also what stops a bad new version in a rolling update: no ready v2 Pod, no next step (see the rolling-update figure on The real chain).

Say the difference - the same words in every lesson

Container vs Pod

A container is one isolated process from an image. A Pod is Kubernetes' wrapper around one or more containers that share a network address.

Kubernetes schedules Pods, not single containers.

Restart vs replace

Restart: the kubelet starts a crashed container again on the same node. Replace: a new Pod is made, often on another node.

A lost node always means replace.

Docker vs containerd

Docker builds images (and runs them on a laptop). containerd runs containers on Kubernetes nodes.

Both use the same OCI image format.

Container vs virtual machine

A container is an isolated process on a shared kernel. A VM is a whole pretend computer with its own OS.

Light and fast vs strong wall. In the cloud, containers often run on VMs.

Image vs container

The image is the fixed package in the store. The container is that image running.

The same pair as artifact vs running app, from lesson 0001.

Desired state vs actual state

Desired is what you wrote should be true. Actual is what really runs now.

A controller closes the gap. When the gap stays open, that is drift.

Imperative vs declarative

Imperative: you give the steps. Declarative: you give the end result, and a tool works out the steps.

kubectl scale is imperative. kubectl apply -f with a file is declarative. Lesson 0005 builds on this.

Cards for your deck

The API works on a laptop but not on the server. Which idea fixes it, and how?

Pack it as a container image: it carries its own libraries, so it no longer depends on the server.

A node dies at night. Who starts the missing copies?

A controller: it sees fewer copies than the desired state says and starts new ones.

Ben scales by hand; Git says 3. What is the risk if nobody notices?

Drift: the written desired state is wrong about reality, and the next sync may undo Ben's change by surprise.

When would you pick a VM over a container?

When you need a strong wall: its own kernel, for example between customers.

Why is the database often a managed cloud service?

Its data must survive: backups, safe disks, careful upgrades. The cloud runs that for you.

Is kubectl apply -f api.yaml imperative or declarative?

Declarative: the file says the end result, and Kubernetes works out the changes.
