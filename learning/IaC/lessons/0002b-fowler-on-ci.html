Warm-up from lesson 0002

1 · The big idea

The big idea

Continuous Integration - the one thing (course line)
Merge small changes daily, each checked automatically - instead of one painful merge weeks later.
Fowler's definition, in plain words
Everyone on the team merges their work into one shared codebase at least once a day, and an automatic build with tests checks each merge, so integration errors show up fast.
The promise
Less risk that delivery runs late, less time lost to integration, and a healthy codebase that lets the team add features fast.
Fowler's opening memory
A warehouse of programmers who had spent months integrating code that had taken years to write. His lesson from it: integrating many developers' work, done late, is long and unpredictable.

3 · Three styles of integration

Fowler compares three ways a team can bring its work together. Read the picture first, then the table.

StyleWhen work is mergedWhat each merge is likeFowler's view
Pre-release integrationOnce, near the release - months or years apartHuge, late, hard to predictThe old normal that CI was made to replace
Feature branchesWhen a feature is finishedA batch of changes; each push makes integration work for everyone else"Semi-integration": you pull from mainline, but your work is not shared until the end
Continuous IntegrationEveryone pushes and pulls at least dailyMany merges, each small: hours of work, not daysCombining a few hours of work is much easier than combining several days

Fowler notes that feature branches become CI if every feature takes less than a day. Otherwise the two are mostly exclusive.

4 · Why more often hurts less

Fowler also warns about the wrong lesson: after a painful integration, a team may decide to integrate less often - which makes the next one worse.

Check - read the curve

A team merges every two weeks. Each merge takes two days to sort out. Someone says: "Let's merge monthly, then we only lose two days a month."

Reveal

It gets much worse than two days. A month of changes is about twice the code of two weeks, so by his rule of thumb about four times the integration work - and more surprises.

Why: the pain grows faster than the gap. Fowler's answer runs the other way: merge more often, so each merge is small enough to take minutes.

What makes this work, by Fowler's account: self-testing code. Version control can merge two changes that both compile and still conflict in meaning. Only the tests catch that kind of conflict - Fowler calls it a semantic conflict - so he calls self-testing code a necessary prerequisite for CI.

5 · The eleven practices

Fowler lists eleven practices, in this order. The colour groups are added here only to make them easier to remember: Codebase what you build from, Rhythm how often and how fast, Safety how you stay safe while moving fast.

  1. CodebasePut everything in a version-controlled mainlineEverything needed to build and run the product is in source control. A clean machine can rebuild it. One shared mainline is the next production version.
  2. CodebaseAutomate the buildScripts or a build tool do every step. Anyone can check out on a clean machine, run one command, and get a running system.Key number: one command
  3. CodebaseMake the build self-testingAn automatic test suite runs on every build and any failing test fails the build. A bug put in on purpose must turn the build red.Key number: any failing test fails the build
  4. RhythmEveryone pushes to the mainline every dayPull, fix conflicts, build locally, push - at least daily; experienced teams more often. Kent Beck's guideline: no code stays unintegrated more than a couple of hours.Key number: at least daily
  5. RhythmEvery push to mainline triggers a buildA CI service builds the mainline head after every push, so a failure points to the latest push. Watch the mainline, not feature branches.Key number: every push
  6. RhythmFix broken builds immediatelyA red mainline comes before other work. The usual fix is to revert the last commit. A "pending head" can stop bad commits from landing at all.Key number: revert first
  7. RhythmKeep the build fastThe XP guideline is ten minutes; an hour is not reasonable. A deployment pipeline splits a fast commit build from slower secondary builds.Key number: 10 minutes
  8. SafetyHide work-in-progressUnfinished work goes into the mainline but stays hidden from users: keystone interface, feature flags, dark launching, branch by abstraction, parallel change.Key number: latent code is still production quality
  9. SafetyTest in a clone of productionSame database versions, OS, libraries, addresses and ports as production. Containers make this practical.
  10. SafetyEveryone can see what is happeningBuild status on dashboards, chat and even red/green lights. Show success too, so people learn the normal rhythm.
  11. SafetyAutomate deploymentScripts deploy to any environment, ideally building it from scratch. This enables automatic rollback, blue-green and canary. Show the build ID in the running app.Key number: several times a day

6 · The comparisons Fowler draws

PairFowler's answer, in plain words
CI vs trunk-based developmentTreated as the same thing. The name trunk-based development came up because people ran CI services on feature branches and called that CI. Fowler keeps the name CI, partly so Kent Beck's work is not renamed away.
A CI service on feature branches vs CIThat is not CI - it is semi-integration. He suggests such tools are really "continuous build services".
CI vs feature branching, together?Generally no - unless every feature takes less than a day. Personal branches are fine if you still push to mainline continuously.
CI vs Continuous DeliveryCI is about integrating in the team's own environment. Continuous Delivery keeps the product releasable at any time, so release becomes a business decision. The separate idea grew from complicated paths to production in early-2000s projects.
Continuous Delivery vs Continuous DeploymentContinuous Deployment releases every commit that passes the pipeline. Continuous Delivery is its prerequisite.
Pull requests vs CI's rhythmReview before merge adds waiting that can break the daily rhythm. Teams keep the flow with pair programming, Ship/Show/Ask, or reviews that refine code after it is merged.
DatabasesPramod Sadalage's Evolutionary Database Design: small, version-controlled migration scripts that run on test and production databases alike.

7 · What CI gives - and when it does not fit

BenefitWhy, in Fowler's argument
Less risk of late deliverySmall, frequent merges rarely bring surprises. A late integration phase is hard to predict and pushes the release.
Less time lost to integrationRoutine small merges take minutes, not days. The cost of big merges is what makes people merge less.
Fewer bugsTests catch conflicts in meaning, and a small diff is easy to debug. He points to DORA research that links frequent integration to better delivery.
Refactoring stays possibleWithout long, risky merges, the team can keep cleaning the code, so cruft does not pile up.
Release becomes a business decisionA mainline that is always ready means shipping is running a pipeline, not a project.

When not to use CI

  • Classic open source - occasional contributors and busy maintainers. Pull requests and feature branches fit that model better.
  • No safety net yet - without a strong test suite, automation and the discipline to keep the build green, CI turns into constant breakage.
  • Not a talent filter - Fowler says CI does not need exceptional developers; steady habits matter more than brilliance.

His final thought ties it back: most work is changing existing code, a messy codebase slows every change, and CI together with self-testing code is what makes regular refactoring - and so a codebase that keeps improving - possible.

8 · How to start - Fowler's advice

  1. Know why. Pick the benefits that matter in your context. Less integration waste shows early; the refactoring benefit takes longer.
  2. Build the skills. Self-testing code helps even before you merge more often.
  3. Set a concrete goal, such as halving how long feature branches live. Reaching it may need better build and test automation and smaller pieces of work.
  4. Use review before merge on purpose: to check tests and to push for smaller commits.
  5. New project? Start with CI from day one, and act fast if the build grows past about ten minutes.
  6. Get help from someone who has done it before - even if it costs money.

Jez Humble's three-question test

Cards for your deck

A team says "we do CI - Jenkins builds every branch". Merges happen every two weeks. What is it really?

Semi-integration. A build service on branches is not CI; the work is not shared until the merge.

The mainline is red and the fix will take an hour. What does Fowler's practice say?

Revert the last commit now to get back to green, then fix it calmly.

Your build takes an hour. What is Fowler's way out?

A deployment pipeline: a fast commit build with test doubles, and a slower secondary build for end-to-end tests.

Why pull again just before you push?

To find a teammate's change that breaks your code - on your machine, not on the mainline (step 4 of the day).

Name three of the five ways to hide work in progress.

Any three of: keystone interface, feature flags, dark launching, branch by abstraction, parallel change.

What are Humble's three questions?

Daily pushes to a shared mainline? A build with tests on every push? Green again within 10 minutes when it breaks?
