The real chain: from code to a running Pod

The lessons teach the ideas: artifact, deployment, desired state, the floor. This page shows what those ideas are in a real Kubernetes company - which file, which tool, which step. You follow one change, "pin a note" in Notekeeper's API, from a laptop to a user, with the infrastructure under it.

How to read this page. Every step names its lesson word. "Sources" under a step names the doc a fact comes from. "Common practice" marks what many companies do but no single doc defines. This is the usual set-up in a Kubernetes shop, not the only one - see "Not every company works like this".

The big idea

The chain - the one thing
One fixed image travels from CI to the cluster; Git says which image runs where - instead of people copying apps onto servers.
In a paragraph
A developer pushes code. CI tests it, builds a container image and pushes it to a registry. Then a one-line commit to Git says "production runs this image now". Argo CD sees that commit, turns the Helm chart into plain Kubernetes YAML, and makes the cluster match it. Inside the cluster, a chain of controllers turns that YAML into Pods, and the kubelet on each node pulls the image and starts the containers. Under all of it is the floor - network, cluster, database - built with IaC on its own, slower road.
Picture
A parcel and a delivery note. The parcel (the image) is packed once and never opened. The delivery note (Git) says which parcel goes to which address. The courier (Argo CD) reads only the note.
Where the picture stops working
A courier carries the parcel. Argo CD never carries the image: it writes the desired state into the cluster, and each node fetches the image from the registry itself.

The chain in six lines

Say these from memory. Line 4 is the one people most often forget.

  1. The developer writes the code and the Dockerfile.
  2. CI builds the image and pushes it.
  3. The registry stores the image.
  4. Git says which image version runs where, with which settings (Helm values).
  5. Argo CD makes the cluster match Git.
  6. Kubernetes runs containers from that image, inside Pods.

Two words to keep apart: the registry holds the image. A container exists only while an image runs, on one node. Claim 2 below tests this.

Step by step

Each step: what happens, a real file or command, then the step in lesson words.

Steps 1-2: the inner loop and CI

The developer writes code and a Dockerfile, the recipe for the image. Each line of the recipe makes one layer. Layers are why images are fast to rebuild and to pull: a layer that did not change is reused.

Notekeeper's API: Dockerfile (app repo)

FROM node:22-slim              # base layer: a small Linux + the Node.js runtime
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev          # the libraries - reused while package.json is the same
COPY . .                       # the code - the layer that changes on most commits
CMD ["node", "server.js"]      # what runs when a container starts

The push (or a pull request) starts a CI workflow. Fast checks run on the code first: lint and unit tests. Then CI builds the image, and checks that need the image run after it: a security scan, integration tests. Only an image that passed is pushed.

Step 3: the registry - and the name of an image

CI pushes the image to a registry: Amazon ECR, GitHub Container Registry, Docker Hub. A full image reference has four parts:

The tag is a name people read. Someone can push other bytes under the same tag, unless the registry blocks it (ECR has an "immutable tags" setting). The digest is a hash of the image's manifest - the list of its layers - so a digest always means the same bytes.

Step 4: the Git hop

The new image sits in the registry, and nothing runs it yet. Something must change Git to say "production now runs 1.4.2". Usually that is one line in a Helm values file in a separate config repo:

Config repo: envs/prod/values.yaml - the whole deploy decision

image:
  repository: 123456789012.dkr.ecr.eu-north-1.amazonaws.com/notekeeper-api
  tag: "1.4.1"
  tag: "1.4.2"

Step 5: Argo CD and Helm

Argo CD checks the config repo about every 3 minutes by default, or at once when the Git server sends it a webhook. It renders the Helm chart with the values file (helm template) and compares the result with the live cluster. A difference = OutOfSync. With automated sync on, Argo CD sends the new desired state to the Kubernetes API server at once. With it off, the app stays OutOfSync until a person presses Sync - one more place for the Continuous Delivery button.

Config repo: the Argo CD Application for production

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: notekeeper-api-prod
spec:
  source:
    repoURL: https://github.com/acme/notekeeper-config   # which repo
    path: charts/notekeeper-api                         # which chart
    helm:
      valueFiles: [../../envs/prod/values.yaml]         # which values
  destination:
    server: https://kubernetes.default.svc              # which cluster
    namespace: notekeeper
  syncPolicy:
    automated: { selfHeal: true }                       # sync by itself, undo hand edits

Steps 6-10: inside the cluster

The API server stores the new spec. Then a chain of loops does the work, each one watching one kind of object (see "Who watches what" below). The Deployment sees a new image and starts a rolling update: it makes a new ReplicaSet for v2 and moves Pods from the old ReplicaSet to the new one, a few at a time. For each new Pod, the scheduler picks a node, and the kubelet on that node has containerd pull the image by digest and start the containers.

What does "ready" mean? Two health checks, called probes, run by the kubelet:

  • Readiness probe - "can this Pod take traffic now?" Until it passes, the Service sends no traffic to the Pod, and the rolling update waits. This is how a bad v2 stops the rollout before users see it.
  • Liveness probe - "is this container still working?" When it fails, the kubelet restarts the container.

Steps 11-12: to the user

A Service gives the API's Pods one stable address and spreads traffic across the ready ones. An Ingress and a cloud load balancer bring traffic in from the internet. Now the change is deployed. It is released when users can use the pin button - the same moment, or later, with a feature flag or a canary (Argo Rollouts).

Helm: where the YAML comes from

What it really solves: one set of Kubernetes YAML for many environments - instead of copying 300 lines per environment and editing them by hand. A chart is YAML templates with blanks. A values file fills the blanks for one environment.

1 · A line in the chart (templates/deployment.yaml)

image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
replicas: {{ .Values.replicas }}

2 · The blanks for production (envs/prod/values.yaml)

image: { repository: …/notekeeper-api, tag: "1.4.2" }
replicas: 3

3 · What helm template prints - plain YAML that Kubernetes reads

image: "…/notekeeper-api:1.4.2"
replicas: 3
  • A second artifact. A chart has its own version and can be pushed to the same registry as the image (an OCI registry). So one release often has two artifacts: the image version and the chart version. Source: Helm: Use OCI-based registries.
  • Helm and IaC. A chart is to Kubernetes YAML what a module is to Terraform code (lesson 0007): reusable code with inputs. A values file per environment is like a set of input variables per environment.
  • The look-alike: Helm vs Kustomize. Helm: templates with blanks, packaged and versioned. Kustomize: plain YAML plus patches, no templates. Many teams use one, some use both.

Docker builds, containerd runs

"Docker" names two things: the tool that builds images, and the engine that once ran them in clusters. Since Kubernetes 1.24 (May 2022), the kubelet no longer talks to Docker Engine - the adapter for it, the dockershim, was removed. On a current cluster the runtime is usually containerd; EKS node images from 1.24 on have containerd only. An image built with Docker still runs, because both sides use the same standard image format (OCI).

The infra lane: who builds the floor

Before any Pod runs, the floor must exist: a network, a cluster, a database, buckets. In most Kubernetes shops an IaC tool builds it, on its own road - the infrastructure pipeline of lesson 0008. That road is slower and more careful, because a mistake can destroy data.

Claims to test

Eight claims you will hear at work. Some are true, some are false. Bet first - true or false, and why - then open the reveal.

Claim 1

"Argo CD deploys when a new image lands in the registry."

Reveal

False. Argo CD watches Git. A new image in the registry changes nothing until Git says to use it. Argo CD compares the desired state in Git with the live cluster.

Why: Git is the one place that says what is true (lesson 0003, moment 4). Registry watching exists only as an add-on: Argo CD Image Updater sees a new tag and writes it to Git, and then the normal Argo CD flow runs. Sources: Argo CD docs, Image Updater docs.

Claim 2

"The container moves from the laptop to CI, to the registry, to Kubernetes."

Reveal

The image moves. A container never moves. The image is the fixed package: CI pushes it to the registry, and each node pulls a copy. A container is one running copy of that image: it starts, runs and stops on one node.

Why: this is lesson 0001's pair, artifact vs running app, one level down: image vs container. Keeping them apart shows where to fix a problem - a bad image is fixed in CI, a bad container in its config or on its node.

Claim 3

"To roll production back, revert one line in Git."

Reveal

True, in a GitOps shop. git revert puts tag: "1.4.1" back in the production values file. Argo CD sees the change and syncs, and the Deployment rolls back to the old image the same way it rolled forward.

Why: Git holds the desired state, so changing Git is how you change what runs - forward or back. Two conditions: the old image must still be in the registry (watch the clean-up rules), and the app must sync, either by itself (automated sync) or when a person presses Sync. A database change that v1.4.2 made is not undone by this - that is the floor's problem, not the image's.

Claim 4

"notekeeper-api:1.4.2 always means the same bytes."

Reveal

False, unless the registry blocks it. A tag is a label. Someone can push other bytes under 1.4.2. The digest (sha256:…) is a hash of the content, so it always means the same image.

Why: promotion (lesson 0002) needs the same artifact in staging and production. Teams get that with a digest, or with immutable tags - an ECR setting that refuses a push to a tag that exists. Sources: Kubernetes: Images, Amazon ECR: tag mutability.

Claim 5

"When a node dies, Kubernetes restarts the container on another node."

Reveal

Nothing moves or restarts. A new Pod is made. The ReplicaSet sees fewer Pods than wanted and makes a new one. The scheduler puts it on a healthy node, and that node's kubelet starts fresh containers from the image.

Why: a restart is a different thing - the kubelet restarts a crashed container on the same node. Lost node = replace; crashed process = restart. This is why containers must be throw-away (lesson 0003, moments 3 and 5).

Claim 6

"If v2 starts but never becomes ready, users keep getting v1."

Reveal

True. The Service sends traffic only to ready Pods, so the failing v2 Pod gets none. With 3 replicas and the defaults (surge 1, unavailable 0), no v1 Pod is removed until a v2 Pod is ready - so the rollout stops at "3 × v1 + 1 v2 not ready".

Why: the readiness probe is the gate. Two limits: Kubernetes does not roll back by itself - the Deployment is only marked as stuck after its progress deadline (10 minutes by default), and a person or a tool must act. And with no readiness probe at all, a Pod counts as ready as soon as its containers start. Source: Kubernetes: Deployments.

Claim 7

"Run helm list to see what Argo CD deployed."

Reveal

Nothing from Argo CD. Argo CD runs helm template only, then applies the plain YAML itself. No Helm release is made, so Helm has nothing to list. Look in Argo CD instead (argocd app list, or the UI).

Why: only one tool can own an app's life cycle. With Argo CD, it is Argo CD - Helm is only the template engine. Source: Argo CD: Helm.

Claim 8

"Kubernetes nodes run containers with Docker."

Reveal

False for a current cluster. Kubernetes removed the dockershim in 1.24. EKS node images from 1.24 on use containerd only. Docker still builds the images.

Why: build and run are separate jobs that share one image format (OCI). That is why an image built with Docker runs fine under containerd. Sources: Dockershim removal FAQ, AWS containers blog.

Say the difference - the same words in every lesson

Image vs container

The image is the fixed package in the store. The container is that image running.

The image moves (CI → registry → node). A container never moves.

Container vs Pod

A container is one isolated process from an image. A Pod is Kubernetes' wrapper around one or more containers that share a network address.

Kubernetes schedules Pods, not single containers.

Tag vs digest

A tag is a name people read, and it can be moved. A digest is a hash of the content, and it never changes.

"The same artifact" needs a digest, or tags that the registry keeps fixed.

Docker vs containerd

Docker builds images (and runs them on a laptop). containerd runs containers on Kubernetes nodes.

Both use the same OCI image format.

helm install vs helm template

helm install puts a chart into the cluster and Helm owns its life cycle. helm template only prints the YAML; another tool applies it.

Argo CD uses helm template. So helm list shows nothing.

App repo vs config repo

The app repo holds the code and the Dockerfile. The config repo holds what runs where: charts, values, Argo CD Applications.

Common practice: a code change and a deploy decision get separate commits.

Restart vs replace

Restart: the kubelet starts a crashed container again on the same node. Replace: a new Pod is made, often on another node.

A lost node always means replace.

Readiness vs liveness

Readiness: "can it take traffic now?" - a failing Pod gets no traffic. Liveness: "is it still working?" - a failing container is restarted.

Readiness also gates a rolling update: no ready v2, no next step.

Cards for your deck

A new image is in ECR. Why is nothing deployed yet?

Git still says the old tag. Argo CD watches Git, not the registry.

What makes "the same artifact" really the same in staging and production?

The digest - or immutable tags in the registry.

Which one line is the deploy decision in a GitOps shop?

The image tag in the environment's values file in the config repo.

Who pulls the image onto a node?

The kubelet on that node, through the container runtime (containerd).

3 replicas, default rolling update. Most Pods at once? Fewest ready?

4 at most (surge 1). Never fewer than 3 ready (unavailable 0).

v2 starts but never becomes ready. What do users see?

Nothing new: the readiness probe keeps traffic on v1, and the rollout stops.

Why does helm list show nothing in an Argo CD cluster?

Argo CD runs only helm template and applies the YAML itself. No Helm release exists.

A node dies. Is the container restarted elsewhere?

No. A new Pod is made and scheduled on a healthy node.

Who usually builds the EKS cluster and the RDS database?

An IaC tool (OpenTofu / Terraform) on the infra road - not the app pipeline.

The six lines of the chain?

Developer writes code. CI builds the image. Registry stores it. Git says what runs where. Argo CD makes the cluster match Git. Kubernetes runs containers in Pods.
