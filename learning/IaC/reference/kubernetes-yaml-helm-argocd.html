Kubernetes YAML, Helm and Argo CD

What this sentence really means: Kubernetes YAML, rendered from a Helm chart and a values file, applied by Argo CD. Follow one chart value through rendering, synchronization and Kubernetes reconciliation.

Scope. The main example uses a chart in Git and Argo CD's built-in Helm support. A chart fetched directly from a Helm repository has different source fields. Other delivery tools and custom Argo CD plugins can behave differently.

The big idea

The one thing
One reusable definition, one environment-specific choice and one delivery loop - instead of copied YAML and manual deploy commands.
In a paragraph
A Helm chart supplies parameterized templates. A values file supplies chart-specific settings. Helm renders them into concrete Kubernetes manifests. Argo CD compares those manifests with the destination cluster and synchronizes differences through the Kubernetes API. Kubernetes controllers then work continuously to make actual state match the requested state.
Picture
A form with blanks, a sheet of answers, a courier and a building supervisor. Helm fills in the form. The values file supplies the answers. Argo CD delivers the completed form and checks for later changes. Kubernetes supervises the building after accepting the form.
Where the picture stops working
Kubernetes does not execute a form like a script. It stores API objects, and independent control loops keep reacting to them. Also, a successful delivery does not prove that the application is healthy.

Words you need

A YAML representation of a Kubernetes API object.
Template
A file containing fixed text and expressions that Helm evaluates.

A named input used by a template, such as image.tag.

The data Helm uses for those inputs.

Evaluate templates with values and produce manifests.

Why Helm exists in this example

You want the same web application in test and production. Test needs one replica. Production needs three. Without templates, you could copy the Deployment YAML and edit each copy. Helm lets you keep one template and give each environment different inputs.

These are only the two lines that matter inside a larger Deployment template:

replicas: {{ .Values.replicaCount }}
image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"

Parameterized template means exactly this: the output depends on named inputs. Here the inputs are replicaCount, image.repository and image.tag.

  • {{ ... }} marks an expression for Helm to evaluate.
  • .Values means "look in the combined values data".
  • .Values.image.tag means "find image, then find tag inside it".

What "a values file supplies configuration" means

The chart has default values in values.yaml:

replicaCount: 1

image:
  repository: ghcr.io/example/web
  tag: "1.0.0"

A delivery engineer also keeps values-production.yaml in Git. This warm-up shows it after the tag change to 1.5.0; section 3 shows the same file before, at 1.4.2.

replicaCount: 3

image:
  tag: "1.5.0"

Helm reads both files. The production file overrides two defaults. It does not specify image.repository, so the default repository remains.

Helm uses the combined values to produce these plain YAML lines:

replicas: 3
image: "ghcr.io/example/web:1.5.0"
No automatic connection. A value does not go directly to Kubernetes or into the application. It has an effect only where a template uses it. Writing replicaCount: 3 in a values file does nothing if no template or dependency consumes replicaCount.

Where Helm takes over

Helm takes over for rendering only: after Argo CD has the source files and before Argo CD compares the rendered manifests with the live cluster.

  1. An engineer changes image.tag in values-production.yaml and merges the Git change.
  2. Argo CD refreshes the Application and resolves its configured Git revision.
  3. Argo CD's repository server gets the chart and values for that revision.
  4. The repository server invokes Helm's template-rendering operation. Helm reads the defaults and overrides, evaluates the templates and returns manifests.
  5. That rendering operation finishes. No Helm process stays behind to watch the files or the workload.
  6. Argo CD's application controller compares the returned manifests with live objects. A relevant difference makes the Application OutOfSync.
  7. A manual or automated sync sends the required API operations to the destination cluster.
  8. The Kubernetes API server accepts and stores the updated Deployment object if the request passes its checks.
  9. The Deployment controller sees the changed Pod template and manages a rollout through ReplicaSets and Pods.

The same rendering step on your laptop

helm template web ./charts/web \
  --values ./charts/web/values-production.yaml

This prints the rendered manifests. It does not change a cluster and does not create a Helm release. With Argo CD, you do not follow it with helm install: Argo CD performs the sync.

helm install vs helm template

helm install puts a chart into the cluster and Helm owns its life cycle. helm template only prints the YAML; another tool applies it.

Argo CD uses helm template. So helm list shows nothing for this built-in flow.

Template change vs values change

A template change alters the reusable resource definition. A values change supplies different input to that definition.

Changing only the image tag leaves the template file untouched.

The short version

  2. A values file supplies configuration for those templates.
  3. Helm renders the templates into concrete Kubernetes manifests.

1. What Kubernetes YAML actually is

What it really solves: a portable description of desired API objects - instead of a person issuing a private sequence of server commands.

Kubernetes YAML is usually a manifest: a YAML representation of one or more Kubernetes API objects.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  • apiVersion: which Kubernetes API group and version to use.
  • kind: the object type - here, a Deployment.
  • metadata: identity, such as the object's name and namespace.
  • spec: the desired state you are requesting, for object kinds that have a spec.

A live object commonly also has status, which Kubernetes components update to report observed state. Desired state and observed state are different.

The declaration, not a script

The example says: "I want a Deployment named web, with three desired replicas." It does not say that three Pods already run. Submitting the declaration asks the API server to create or update an object. Controllers do the later work.

YAML is an input format. Kubernetes persists API object state, not necessarily your YAML bytes. Live objects can contain defaults, system-generated metadata and observed status.

2. What a Helm chart is

What it really solves: one reusable set of Kubernetes resources with inputs - instead of copied manifests for every environment.

A Helm chart is Helm's packaging format: a collection of files describing a related set of Kubernetes resources.

web/
├── Chart.yaml
├── values.yaml
└── templates/
    ├── deployment.yaml
    └── service.yaml
  • Chart.yaml contains required chart metadata, including its name and chart version.
  • values.yaml contains the chart's default configuration values.
  • templates/ contains parameterized templates for Kubernetes manifests.
Chart is not image. A container image contains software that can run. A chart contains templates and configuration for requesting Kubernetes resources. A chart often refers to a container image through its values. The chart version, the chart's informational appVersion and the container-image tag are separate concepts.

A template contains expressions

For example, templates/deployment.yaml might contain:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"

The {{ ... }} expressions are Helm template syntax, built around Go templates. Helm evaluates them during rendering.

3. What the values file does

What it really solves: environment-specific choices without editing the reusable templates - instead of maintaining a copied chart per environment.

A values file is plain YAML containing chart-specific configuration data. Start with the chart's defaults in values.yaml:

replicaCount: 1

image:
  repository: ghcr.io/example/web
  tag: "1.0.0"

Then provide values-production.yaml:

replicaCount: 3

image:
  tag: "1.4.2"

Helm combines these values. Your values override matching defaults; unrelated defaults remain available. Nested mappings are merged rather than treating your file as a wholesale replacement for the defaults file.

Three merge traps.
  • Lists are replaced, not merged. If the defaults have env: [A, B] and production sets env: [C], the result is only [C]. Only mappings (key: value blocks) merge.
  • null removes a default. resources: null in an override deletes the chart default key.
  • Quote version-like values. YAML reads tag: 1.10 as the number 1.1. tag: "1.10" stays a string. That is why the examples quote tags.

The effective values here are therefore:

replicaCount: 3

image:
  repository: ghcr.io/example/web  # inherited default
  tag: "1.4.2"                     # overridden

After rendering, the Deployment includes:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: "ghcr.io/example/web:1.4.2"

Two consequences

  • Rendering produces configuration; it does not itself deploy anything.
  • Values have an effect only where the chart uses them. The key replicaCount is not intrinsically meaningful to Kubernetes. It matters here because this chart passes .Values.replicaCount into the Deployment.

Different charts expose different value names and structures. Read the particular chart's values.yaml, documentation and optional values schema. With multiple values files, later files have higher precedence for duplicate keys. On the Helm CLI, --set beats every --values file.

In Argo CD the order is: parameters > valuesObject > values > valueFiles > the chart's own values.yaml. Within valueFiles, the last file listed wins.

Render it locally

You can reproduce basic rendering with:

helm template web ./charts/web \
  --values ./charts/web/values-production.yaml \
  --namespace production

This prints rendered manifests. Despite accepting a name argument, helm template does not install a Helm release.

4. Where Argo CD fits

What it really solves: continuous delivery from a declared source to a cluster - instead of people remembering when and where to run deploy commands.

Argo CD is a GitOps continuous-delivery tool implemented as a Kubernetes controller. It compares desired application configuration with resources in a destination cluster and performs synchronization.

You normally define an Argo CD Application custom resource. For a Git-hosted chart:

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: web
  namespace: argocd
spec:
  project: default

  source:
    repoURL: https://github.com/example/platform.git
    targetRevision: main
    path: charts/web
    helm:
      valueFiles:
        - values-production.yaml

  destination:
    server: https://kubernetes.default.svc
    namespace: production

  syncPolicy:
    automated:
      prune: true
      selfHeal: true
This Application is configuration for Argo CD, not one of the rendered workload manifests. Its metadata.namespace: argocd assumes the usual Argo CD installation namespace.
FieldWhat it selects in this example
source.repoURLThe Git repository containing the desired configuration.
source.targetRevisionThe Git branch main. It could also identify a tag or commit.
source.pathThe chart directory charts/web inside the repository.
source.helm.valueFilesThe values files used for Helm rendering. Paths here are relative to source.path.
destination.serverThe destination cluster's API endpoint.
destination.namespaceThe namespace for namespace-scoped resources whose manifests omit metadata.namespace.

The values-file path therefore resolves to charts/web/values-production.yaml. destination.namespace does not blindly replace every explicit namespace in every manifest.

For a chart fetched directly from a Helm repository rather than Git, source.chart identifies the chart and targetRevision identifies its chart version. source.path is not used for that source form.

Three details the Application decides for Helm

  • Values from another repository. valueFiles paths are relative to the chart. To keep values in a different repo than the chart (common with a chart from a Helm repository), use spec.sources (multiple sources, Argo CD 2.6+) and point at the other repo with a $ref prefix, for example $values/envs/values-production.yaml.
  • Release name. .Release.Name defaults to the Application name (web here). Override it with source.helm.releaseName. Changing it later can rename every resource whose name the chart builds from the release name.
  • Namespace. Argo CD renders with the destination namespace, so .Release.Namespace is production here.

5. The complete sequence

Follow the change from Git to its observed outcome. Select Run it to reveal the moments in order.

Read moment 5 carefully. "Together" means independent activity, not a guaranteed order. Argo CD can report Synced while rollout health is still Progressing. A later failure can make health Degraded without changing the desired Git revision.
MomentWhat changesWhat has not been proved yet
Git mergeThe source now requests 1.5.0.Nothing has changed in the cluster.
Helm renderingThe manifest now contains image 1.5.0.No API operation has happened.
ComparisonArgo CD sees desired 1.5.0 and live 1.4.2.The new version has not been applied.
SyncThe API server accepts the updated Deployment.New Pods are not necessarily running or ready.
ReconciliationControllers create and schedule replacement Pods.The rollout can still stall or fail.

Step 1: you change Git

You might change:

image:
  tag: "1.4.2"

to:

image:
  tag: "1.5.0"

and commit that change. Changing the values file does not itself build a new container image. Building and publishing the image is normally a separate CI step.

Step 2: Argo CD resolves the source

Argo CD determines which Git revision the Application currently targets and obtains the chart and values. Its repository server generates Kubernetes manifests from the repository, revision, path and template-specific settings.

When does Argo CD notice the commit? By default it polls Git about every 3 minutes (timeout.reconciliation: 120s plus up to 60s jitter). A Git webhook makes it near-instant. A branch such as main is resolved to a specific commit SHA; the Application records that SHA as the synced revision.

Step 3: Helm renders the manifests

With Argo CD's built-in Helm support, Helm renders the chart with helm template.

helm install vs helm template

helm install puts a chart into the cluster and Helm owns its release life cycle. helm template only prints the YAML; another tool applies it.

Argo CD's built-in flow uses Helm to render charts, while Argo CD manages the application life cycle. Do not assume helm list or helm rollback will manage an Application deployed through this flow. Roll back by reverting the Git change (or with Argo CD's own history/rollback, which is not available while automated sync is on).

What changes because Helm only renders

  • Hooks are translated, not run by Helm. pre-install/pre-upgrade become Argo CD PreSync; post-install/post-upgrade become PostSync; hook-weight becomes a sync wave. Argo CD cannot tell install from upgrade, so pre-install and pre-upgrade hooks run on every sync. Rollback and test hooks are ignored. If the chart defines any Argo CD hooks, all Helm hooks are ignored.
  • lookup returns nothing. Rendering does not read the live cluster, so a template that uses lookup (for example, "reuse the existing secret") gets an empty result. Every refresh then sees a new value and the app can stay OutOfSync.
  • Chart dependencies. If Chart.yaml lists dependencies, the repository server fetches them before rendering. Private dependency repositories must be registered in Argo CD.

Step 4: Argo CD compares desired and live state

Argo CD's application controller compares:

  • Desired state: the newly rendered manifests.
  • Live state: the corresponding objects currently in the destination cluster.

If a relevant difference exists, the Application becomes OutOfSync. If the comparison finds no relevant difference, it is Synced.

"Relevant" matters: fields set by the cluster (defaults, status) are not counted, and you can tell Argo CD to skip more with ignoreDifferences. To know which live objects belong to the Application, Argo CD marks each one with the argocd.argoproj.io/tracking-id annotation (the default tracking method; older setups use the app.kubernetes.io/instance label).

Step 5: a sync applies the changes

A sync reconciles the destination cluster with the desired manifests. It can be:

  • Manual: initiated through the UI, CLI or API.
  • Automated: performed when Argo CD detects that an automated Application is OutOfSync.

The normal apply behavior uses declarative kubectl apply; options can change details such as server-side apply. Conceptually, Argo CD submits API operations to create or update resources as needed.

Automated policyWhat it permitsWhat it does not mean
prune: trueAutomated sync can delete Application resources that are no longer present in desired configuration.Ordinary apply does not delete every object missing from a manifest.
selfHeal: trueArgo CD can correct live-cluster drift, such as a hand edit to an Application-managed Deployment.It does not diagnose or repair application health.
  • Both are off by default. With automated: {} alone, removed resources stay in the cluster and hand edits stay too: automated sync reacts to changes in the desired state (Git), not to live drift. Drift only shows as OutOfSync.
  • No automatic retry of a failed commit. If an automated sync of a commit SHA fails, Argo CD does not try that same SHA again unless you set syncPolicy.retry.
  • Self-heal and autoscalers fight. If an HPA changes replicas and the chart also sets replicas, self-heal keeps putting it back. Leave replicas out of the rendered Deployment when an HPA owns it, or ignore that field.

Step 6: the Kubernetes API server processes the objects

For each resource, the destination cluster's API server processes the request, including relevant authentication, authorization, validation and admission behavior.

Accepted object state is persisted in Kubernetes' backing store, normally etcd. A successful API write means the object was accepted. It does not prove that the application is running, ready or available.

Step 7: Kubernetes controllers reconcile

Kubernetes controllers are continuing control loops that move current cluster state toward desired state. For a Deployment, the usual chain is:

  1. The Deployment controller manages ReplicaSets.
  2. A ReplicaSet creates and maintains the desired Pods.
  3. The scheduler selects nodes for unassigned Pods.
  4. On each selected node, the kubelet works with the container runtime to run the containers described by the Pod.

The Deployment manifest contains a Pod template; you do not separately render every ReplicaSet and Pod.

Update vs rollout. Changing the image tag changes the Deployment's .spec.template, so it triggers a rollout. Changing only .spec.replicas changes desired Pod count and does not itself trigger a rollout. This chain is specific to Deployments. Services, ConfigMaps, Jobs and other kinds have different behavior.

6. Synced does not necessarily mean Healthy

Argo CD reports these as separate assessments:

  • Sync status: do the live resource configurations agree with the desired manifests?
  • Health status: do resource-specific health checks indicate that resources are healthy?

For example, the desired Deployment might be applied successfully, making the Application Synced, while its containers repeatedly fail because the configured image cannot run. The Application could then be Degraded.

How long until Degraded? For a Deployment, Argo CD reports Progressing while the rollout is in progress. It turns Degraded when Kubernetes marks the rollout as failed - by default after the Deployment's progressDeadlineSeconds (600 s) passes with no progress. So a broken image can look "only Progressing" for up to 10 minutes.

Health values: Healthy, Progressing, Degraded, Suspended, Missing, Unknown. The Application shows the worst health of its directly managed resources. Sync values: Synced, OutOfSync, Unknown.

Success boundaryWhat it proves
Rendering succeededOutput was generated. It does not prove deployment.
The API operations succeededKubernetes accepted object changes. It does not prove readiness.
Reconciliation and health checks succeededThe workload reached a satisfactory observed state.

The mental model to keep

Think of four separate jobs: Helm generates the configuration; Argo CD delivers it; Kubernetes reconciles it; your container image supplies the software that runs.

The original sentence, rewritten

We keep parameterized Kubernetes resource templates and environment-specific configuration in Git. Argo CD renders them into concrete manifests, applies those manifests to the destination cluster and tracks synchronization. Kubernetes controllers then continuously reconcile the cluster toward the requested state.

Review cards

Say the answer before opening each card.

Does rendering a chart deploy it?

No. Rendering evaluates templates and produces manifests. A separate apply or sync operation changes the cluster.

Does a user values file replace every chart default?

No. Matching values override defaults, and nested mappings are merged. Unrelated defaults remain available.

Why can two charts use different value names?

Values are chart-specific inputs. A value matters only where that chart's templates or dependencies consume it.

Does Argo CD's built-in Helm support run helm install?

No. It uses helm template to render charts. Argo CD manages the application life cycle.

Does a successful API write prove that Pods are ready?

No. It proves that the API operation succeeded. Controllers, scheduling, node execution and health assessment come later.

Does changing replicas trigger a Deployment rollout?

Not by itself. A Deployment rollout is triggered by a change to .spec.template. Scaling changes desired Pod count.

What is the difference between Synced and Healthy?

Synced compares desired and live configuration. Healthy reports resource-specific observed health.

Defaults have a list env: [A, B]. Production sets env: [C]. What is the result?

Only [C]. Lists are replaced; only mappings merge.

Automated sync is on, selfHeal is off. Someone edits the Deployment by hand. What happens?

The Application shows OutOfSync, but Argo CD does not revert the edit. Automated sync reacts to changes in Git, not to live drift.

What is .Release.Name for an Application named web, with no releaseName set?

web. The release name defaults to the Application name.

A chart has a pre-upgrade hook. When does it run under Argo CD?

As a PreSync hook on every sync. Argo CD cannot tell install from upgrade.

Does selfHeal repair a broken application?

Not directly. It corrects live configuration drift. It is not an application-health diagnosis or repair feature.
